# NXN1X 작업 기록: 2026-11-19 ~ 11-20 (N1X 성능과 크래시)

기기: NVIDIA RTX Spark N1X 노트북. 빌드별 상세는 BUILD_LOG.txt(한 줄에 빌드 하나), 소스 백업은 `_backup\<태그>\`에 있습니다. 시간은 한국 시간이고, BUILD_LOG는 UTC입니다.

## 1. 출발점: import 메모리가 N1X에서 느리다

- **측정**(nvidia_report\membench): import(VK_EXT_external_memory_host)한 게임 메모리에서
  - 고정 기능 vertex/index fetch: 100-250배 느림(950 µs 대 3.8 µs)
  - atomic: 약 25배
  - 같은 주소 반복 읽기: 약 36배
  - SSBO store: 약 1.8배
  - SSBO 읽기와 복사(125-160 GB/s)는 정상
- **HWAoI**: 정점 fetch가 원인이었습니다. vbmir(device-local 정점 미러, 64 KB 블록 추적)로 16 → 30 fps, 한때 60 fps에 도달했습니다. vbvol로 보호를 4 KB 단위로 줄였습니다. → 빌드 vtxmir, vbmir, vbvol
- **바요3**: depth pass의 fragment shader가 픽셀마다 SSBO에 써서(import), 그 pass가 40-57 ms였습니다.

## 2. GPU 메모리 캐시 (copy 모드, `NXN1X_POOL_MODE=copy`)

pool을 device-local 사본으로 두고, 제출마다 CPU 변경을 올리고, GPU 변경은 게임 메모리로 병합합니다.

| 단계 | 빌드 | 내용 | 결과 |
|---|---|---|---|
| 1단계 | poolcopy, poolcopy2 | 청크별 사본, shadow, readback, 3-way 병합. 동기화는 직렬(앞 제출 완료를 기다림) | 바요3 depth pass 0.6 ms, GPU 26-32 → 7-9 ms. HWAoI 22-24 fps(대기 8-10 ms) |
| 4 KB 동기화 | stage2a, stage2a2 | dirty 4 KB 페이지만 비교, 64/4096 페이지 묶음 건너뛰기. Memory::Write* 훅 추가 | HWAoI 동기화 10.8 → 3 ms |
| 정점 깨짐 수정 | pcverify, vfix | 진단 스위치로 원인 확정: 코어(MapRegion, ProtectRegion)가 nvn_dirty 몰래 페이지를 RW로 바꿈. 바꾼 직후 write watch에 알리도록 수정 | 바요3 정점 정상 |
| 직렬화 제거 | stage2c, 2c2, 2c3 | 제출별 staging, pre/post GPU 사본, post≠pre로 GPU 변경 판정, 슬롯은 병합 뒤 재사용, 거절 시 복구. 정확 바이트 업로드는 병합 전 GPU 쓰기가 있는 청크에만 | HWAoI 대기 12 → 0 ms, 27 → 37-57 fps. 바요3 무거운 구간 45-58 fps |
| volatile 페이지 | stage2b, 2b2, 2b3 | 자주 쓰이는 CPU 전용 페이지는 보호를 풀고 동기화 때 비교. 진입: 최근 32번 동기화 중 fault 3번 이상 | 정확성 통과. HWAoI fault 감소 효과는 작음 |
| fault-ahead | combined1120 | 순차 fault(P-1 다음 P)이면 P+1..P+15를 한 번에 해제 | HWAoI 이동 중 fault 15-35k/s → 3.4-5.8k/s, fps 37-49 → 52-57 |

- **self-test**: case 0-12, T1-T17, V1-V7, FA1-FA3을 만들었습니다. 병합을 붙잡아 제출 여러 개를 동시에 진행시키는 hold 훅을 씁니다.
  - serial 모드(T11/T12 FAIL)와 naive 모드(반례 FAIL)를 기준으로 남겨 두었습니다.
  - case 8b(counter 보고 순서)는 combined1120에서 처음 통과했습니다.
- **남은 차이**: HWAoI는 import + vbmir에서 60 고정이었지만, copy에서는 이동 중 52-57입니다. CPU 쓰기 추적 비용이 남아 있기 때문입니다.

## 3. NCE 크래시 (0xd, RtlRestoreContext의 SP 검사)

| 빌드 | 원인(증거) | 수정 |
|---|---|---|
| tebfix, tebfix2 | 게임이 다른 스택(fiber)에서 fault한 뒤 재개했는데, TEB 경계가 옛 스택 기준이었음 | SP가 속한 할당으로 경계를 맞춤 |
| x18fix → tebfix3 | 브리지가 guest x18을 TEB로 착각해 호스트 경계를 guest 메모리에 씀. x18fix는 다른 스레드의 TEB를 써서 틀렸음 | 대상 스레드의 TEB를 x4로 넘기고 `mov x18,x4` |
| tebfix4 | 자기 fault 전달 중에 다른 스레드 break가 PC를 브리지로 옮김 | 브리지 구간도 맞춤 대상에 포함 |
| tebfix5 | tebfix4가 VEH 안에서 로그를 찍어 OutputDebugString 예외가 처리되지 못함(17:06) | SP만 보는 규칙 하나로 통일, VEH 경로에서 로그 제거(카운터만) |
| nceresume | Astra 검수 R1-R17 | 공통 ResumeChecked(전환 구간 PC 되돌림, 맞출 수 없으면 0xE0CE0001 fail-fast), 바인딩 seqlock, headroom을 알려진 스택 기준으로, x18 직접 경로 경계 갱신 |

- 그 뒤로 NCE 크래시는 없었습니다. tebfix5의 "left" 카운터는 계속 0입니다.
- 남은 일: P7 단계별 주입 테스트, STP/exclusive 재실행 테스트(실제 guest 스레드가 필요).

## 4. 그 밖의 크래시와 수정

| 증상 | 원인 | 수정(빌드) |
|---|---|---|
| StarFox 약 115초 abort(ucrtbase c0000409) | NVN command memory 상한 1 GB. 게임이 메모리를 콜백으로만 주는데, 콜백 응답 전에 빌려준 host 세그먼트에 guest 범위가 없어 영원히 회수되지 않음(65,489개) | 세그먼트를 콜백이 응답한 청크에 묶고, 게임이 그 청크를 다시 줄 때 회수(combined1120). 274초까지 정상, 세그먼트 773개로 일정 |
| abort 보고 파일이 빔 | 두 스레드 동시 die, SIGABRT 경로 의존 | 이유와 메시지 먼저 쓰기, 원시 주소, die()가 직접 호출(stage2c, stage2c3) |
| 종료 크래시(System::IsPoweredOn) | sv1 watchdog 스레드가 detach된 채 System 해제 뒤 접근 | 종료 때 멈추고 join(combined1120). 이후 재현 없음(확정은 추가 관찰 필요) |
| 19:59 StarFox vk::Exception(MasterSemaphore::Wait) | 일회성, 원인 미확정. A/B 4회 재현 안 됨 | VkResult, device fault, 마지막 제출을 기록하도록 진단 추가(combined1120). 자료는 logs_poolcopy\crash_1959 |
| 글자 일부 빠짐 | 비동기 셰이더가 빌드 중인 파이프라인의 draw를 전부 건너뜀 | 깊이 테스트 없는 draw와 compute는 기다림(glyphwait) |

## 5. 설계와 검수 문서 (design\)

- GPU_MEMORY_CACHE_DESIGN.md, GPU_MEMORY_CACHE_STAGE2_DESIGN.md: copy 모드 1·2단계. Astra와 내부 검수 반영(8절)
- ASTRA_NCE_RESUME_REVIEW_REQUEST.md: NCE 재개 설계. 검수 반영 R1-R17(9절)
- GPU_MEMORY_HYBRID_DESIGN.md, ASTRA_GPU_MEMORY_HYBRID_REVIEW_REQUEST.md: **다음 방향**
  - backing 범위별 import/copy. 느린 GPU 쓰기(shader store, atomic)가 있는 범위만 copy로 바꿉니다.
  - raw global memory 바인딩만으로는 바꾸지 않습니다(OoT의 723 MB pre/post 문제).
  - `NXN1X_POOL_MODE=import` 하나로 전부 되돌릴 수 있습니다.
  - 드라이버가 빨라지면 copy를 자동으로 끕니다.
  - 전제(HWAoI fault의 100%가 GPU가 쓰지 않는 페이지)는 첫 숫자로 성립했습니다.

## 6. 운영 원칙 (NPARK)

- 근본 원인만 고칩니다. 환경 변수 스위치는 A/B 측정용입니다.
- 수정 전에 원인을 증거로 보고합니다. 백업은 `_backup\<태그>`에, BUILD_LOG는 빌드마다 한 줄입니다.
- 게임은 직접 실행하지 않습니다. 빌드는 NXN1X가 꺼져 있을 때만 합니다.
- 테스트는 최소로 합니다. COPY self-test 한 번과, 변경이 노리는 게임 하나입니다.
- 이 스레드는 앞으로 퍼포먼스 문제가 생겼을 때 대응하는 곳입니다. OoT 작업은 별도 스레드에서 합니다.

## 7. 열린 항목

- HWAoI: copy에서 60 고정 회복. 혼합 구현이 목표이고, Astra 검수가 먼저입니다.
- 혼합 전제를 범위 단위·쓰기 종류별로 확인할 카운터(설계 1.1절), attachment와 transfer dst 성능 측정(2절)
- NCE P7 주입과 STP/exclusive 재실행 테스트
- 무한 로딩: 이를 담은 로그(sv1 덤프)가 아직 없습니다.
- T15(GPU 쓰기 진행 중에 CPU가 옛 값을 다시 쓰는 경우)는 알려진 한계로 문서화돼 있습니다.
