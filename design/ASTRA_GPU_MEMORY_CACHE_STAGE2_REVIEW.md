# GPU 메모리 캐시 2단계 설계 검수

- 검수일: 2026-11-20
- 대상: `GPU_MEMORY_CACHE_STAGE2_DESIGN.md`, `ASTRA_STAGE2_REVIEW_REQUEST.md`
- 판정: **현재 §1·§2의 스냅숏 판정식으로 직렬화를 제거하면 안 된다. 4 KB 비교 최적화는 별도 변경으로 진행할 수 있다.**
- 전제: device-local A안과 전체 풀 사본 정책은 유지한다. 메모리 예산·LRU·B안 재검토, DK 실행, 취소한 동일 주소 픽셀 성능 벤치는 이번 검수 범위에 넣지 않는다.

## 1. 결론과 검증 범위

1단계의 제출 대기·비교·fault 비용을 줄이려는 목표는 타당하다. 제출별 upload staging을 불변으로 유지하고, readback을 제출별로 보관하며, 병합 후 `g_done`을 공개하는 방향도 유지할 수 있다.

**문제는 `G != S[e]`를 “그 에폭의 CPU 변경분”으로 해석하는 핵심 성질이다. 이전 제출의 GPU 결과를 병합하는 작업도 G를 바꾸므로, 현재 규칙에서는 이 성질이 성립하지 않는다.**

이 때문에 CPU와 GPU가 서로 다른 필드만 수정해도 다음 두 문제가 발생한다.

- 이전 GPU 병합을 CPU 쓰기로 오인하여 새 GPU 결과를 버린다.
- 이전 GPU 병합값을 다음 CPU 업로드에 섞어 최신 device-local 값을 과거 값으로 되돌린다.

이 두 반례는 **문서의 비교·병합 규칙을 그대로 구현한 순수 Python 모델에서 확인했다.** 프로젝트 코드나 Vulkan 장치를 실행한 결과는 아니다. 소스, 1단계 테스트 본문, 실측 원본 로그가 첨부되지 않았으므로 실제 구현 상태와 기존 12개 테스트의 커버리지는 확정하지 않았다.

## 2. P0-1: CPU는 y만 써도 GPU의 x 결과를 잃는다

### 조건

같은 추적 페이지에 필드 x와 y가 있다.

- 게스트 CPU는 y만 쓴다.
- 게임 GPU 명령은 x만 쓴다.
- 게임 GPU 명령은 y를 읽지도 쓰지도 않는다. y의 업로드·readback은 캐시 구현이 생성한 내부 복사다.
- GPU 제출과 GPU 복사는 올바르게 순서화됐다고 가정한다.
- 완료 스레드는 문서대로 N, N+1 순서로 병합한다.

따라서 같은 주소에 대한 원래 게스트 CPU/GPU data race를 가정한 반례가 아니다. 비중첩 접근을 캐시 구현이 잘못 처리하는 사례다. [S1]

### 문서 규칙을 적용한 순서

| 순서 | 동작 | 게스트 G = (x,y) | 스냅숏·GPU 결과 |
|---|---|---|---|
| 0 | 초기 상태 | (0,0) | D=(0,0) |
| 1 | GPU 제출 N이 x=1 기록. readback 확보, CPU 병합은 지연 | (0,0) | R[N]=(1,0) |
| 2 | CPU가 y=1 기록 | (0,1) | 첫 쓰기 직전 S[N]=(0,0) |
| 3 | N+1에 y=1 업로드 후 GPU가 x=2 기록 | (0,1) | D=(2,1), R[N+1]=(2,1) |
| 4 | CPU가 y=2 기록 | (0,2) | S[N+1]=(0,1) |
| 5 | 완료 스레드가 N 병합 | (1,2) | x에 R[N]=1 적용, CPU의 y=2 보존 |
| 6 | 완료 스레드가 N+1 병합 | **(1,2): 오류** | G.x=1과 S[N+1].x=0이 다르므로 CPU 변경으로 오인 |

정답은 **G=(2,2)**다. 하지만 §2.2의 식은 x=1을 보존한다. CPU는 x를 한 번도 쓰지 않았다.

### 왜 틀리는가

§1은 “GPU 값은 병합 전까지 G에 들어오지 않으므로 G와 S의 차이는 CPU 변경”이라고 설명한다. 그러나 S[N+1]을 만든 뒤 **이전 제출 N의 병합**이 G에 들어올 수 있다.

완료 스레드가 제출 순서대로 병합한다는 조건은 이 반례에서 이미 지켰다. 순서대로 병합해도 서로 다른 시점의 기준본이 자동으로 정합성을 유지하지 않는다.

**S[N]이 그 페이지의 첫 CPU 쓰기 직전 값이라는 사실만으로, R[N]과 현재 G의 공통 기준본이 되는 것은 아니다.**

## 3. P0-2: 이전 GPU 결과가 다음 업로드에 섞여 device-local도 되감긴다

위 표의 5번 직후에 N+2 동기화가 먼저 실행되는 분기를 보자.

| 값 | 내용 |
|---|---|
| 현재 G | (1,2) |
| 비교 기준 S[N+1] | (0,1) |
| 현재 device-local D | (2,1) |
| 문서의 G≠S 비교 결과 | x=1, y=2를 모두 CPU 변경으로 판단 |
| N+2 업로드 후 D | **(1,2): x가 2에서 1로 되돌아감** |

x=1은 CPU 변경이 아니라 N의 내부 readback 결과다. §2.2의 다음 문장은 직렬화를 제거하면 성립하지 않는다.

> 이미 사본과 같은 값이라 실제 업로드는 없습니다.

비교 대상은 최신 D가 아니라 S이며, G에 막 병합한 N의 값과 이미 N+1이 수정한 D의 값은 다를 수 있다.

**내부 copy-back에서 CPU dirty 플래그만 세우지 않는 수정도 충분하지 않다.** 위 반례는 실제 CPU의 y 쓰기 때문에 이미 해당 페이지가 dirty다. 페이지를 비교하면 GPU에서 온 x 차이가 여전히 CPU 업로드에 섞인다.

### 필요한 수정 계약

다음 정보의 의미를 분리해야 한다.

| 정보 | 필요한 의미 |
|---|---|
| CPU 변경 기록 | 게스트 CPU가 만든 변경. 내부 GPU 병합과 구분 |
| 제출별 CPU patch | 확정한 범위·값·에폭·기준 세대. 제출 뒤 불변 |
| GPU readback R[N] | 제출 N의 확정된 GPU 결과 |
| G에 반영된 GPU 세대 | 어떤 GPU 결과까지 CPU 관측용으로 커밋했는지 |
| 열린 에폭의 비교 기준 | 내부 GPU 커밋을 새 CPU 변경으로 오인하지 않는 기준 |

기존 shadow의 두 역할을 분리하는 것은 검토할 수 있다. **두 역할을 S[e] 하나로 대체해 모두 삭제할 수 있다는 증명은 현재 없다.**

내부 GPU 커밋에 맞춰 열린 에폭의 기준을 보정하는 방법을 택한다면, 어떤 에폭의 어떤 바이트를 보정하고 이미 확정된 CPU patch를 어떻게 보존하는지 명시해야 한다. 모든 snapshot을 무조건 현재 G로 바꾸면 아직 업로드하지 않은 CPU 변경을 없앨 수 있다.

GPU에서 확인된 기준과 이후 CPU patch를 분리하는 구조도 후보지만, 이것만 추가하면 완전히 해결된다고 판정하지 않는다. 새 전이 규칙을 작성하고 위 두 반례를 통과해야 한다.

## 4. P0-3: S[N]이 없는 경우와 값 비교의 의미

### S[N]이 없는 정상적인 순서

§2.2는 N+1 이후 CPU 쓰기가 있어도 S[N]을 쓰라고 한다. 하지만 다음 경우가 가능하다.

1. N 이후에는 그 페이지에 CPU 쓰기가 없다.
2. N+1 동기화로 에폭이 증가한다.
3. 그 뒤 첫 CPU 쓰기가 발생하여 S[N+1]만 생성된다.
4. N의 병합이 도착한다.

N 이후 CPU 쓰기는 있었지만 **S[N]은 생성되지 않았다.** 다른 에폭에서 기준을 상속할지, 특정 최초 snapshot을 찾을지, 별도 기준을 둘지 정의해야 한다. 임의로 다른 snapshot을 대신 쓰는 것만으로 R[N]과 공통 기준이 된다고 가정할 수 없다.

“snapshot 없이 dirty이면 전체 페이지 업로드”도 모든 경우에 안전한 fallback은 아니다. 초기 D 구성 전의 첫 업로드와, 진행 중 GPU 결과가 존재하는 페이지의 snapshot 누락을 구분해야 한다.

### 값이 같다는 사실과 쓰기 부재는 다르다

`G == S`여도 CPU가 같은 값을 다시 썼거나 A→B→A로 값을 되돌렸을 수 있다. 따라서 “CPU가 바꾸지 않은 바이트”라는 표현은 정확하지 않다.

단, 이 사실만으로 동기화되지 않은 동일 주소 CPU/GPU 쓰기에 특정 정답을 요구하지는 않는다. 지원해야 할 게스트 동기화 계약에서 어떤 쓰기 순서가 보존돼야 하는지를 정해야 한다.

이번 검수의 주된 실패 증거는 이 논쟁과 무관한 **§2·§3의 비중첩 CPU/GPU 반례**다.

### snapshot의 수명

“그 에폭의 병합이 끝나면 해제”로 끝내지 않는다. 다음 중 하나라도 참조하면 유지해야 한다.

- 아직 확정하지 않은 CPU upload patch.
- 다른 열린 에폭의 병합 판정.
- GPU 커밋에 따른 기준 보정.
- 제출 실패 후 복구.

마지막 사용자를 기준으로 해제해야 하며, 에폭 번호나 GPU 완료 하나만으로 판단해서는 안 된다.

## 5. P0-4: volatile snapshot은 캡처 시점을 통일해야 한다

volatile에서 예외 대신 snapshot을 쓰는 방향은 비교 비용과 fault 비용의 교환이다. **쓰기 추적의 정확성이 자동으로 보완되는 것은 아니다.**

### 문서가 반드시 차단해야 할 순서

| 순서 | 값 |
|---|---|
| 이전 기준 | 0 |
| upload staging으로 G를 복사 | 1 |
| 다른 CPU가 G를 수정 | 2 |
| 새 기준을 G에서 다시 캡처 | 2 |
| 다음 동기화 | G=기준=2이므로 업로드 없음 |

GPU에는 1만 전달됐는데 기준에는 2가 전달된 것처럼 기록된다. 이는 서로 다른 시점의 G를 upload와 다음 기준에 사용하는 구현을 허용하면 생기는 누락이다.

**동기화에서 안정적으로 확보한 하나의 불변 캡처 C[N]을 비교·업로드 payload·다음 비교 기준에 동일하게 사용해야 한다.** 그 캡처 이후의 CPU 쓰기는 다음 세대로 남긴다. 이 조건은 위 누락을 막지만, §2·§3의 내부 GPU 커밋 오분류까지 해결하지는 않는다.

### 보호·prepare·alias에서 필요한 계약

- 같은 페이지의 여러 스레드가 최초 write fault를 낼 때 snapshot이 완성되기 전에 어느 writer도 그 페이지를 바꾸지 않게 한다.
- HLE의 `dm_guest_write_prepare` 호출과 실제 store 사이에 에폭이 바뀌는 경우를 정의한다.
- NCE native store는 일반 호스트 mutex를 자동으로 획득하지 않는다. snapshot 저장소의 락과 실제 G의 쓰기 통제는 다른 문제다.
- 같은 backing의 모든 VA alias에서 dirty·epoch·snapshot·보호 전이를 연결한다.
- 내부 GPU 병합, 게스트 CPU 쓰기, 단순 prepare 호출을 분류한다.
- snapshot·재보호 중 새 쓰기를 이전 에폭의 clean 처리로 지우지 않는다.
- 보호된 G를 completion 스레드가 직접 처리할 때 재귀 fault와 자기 대기를 막는다.

Windows 보호는 지정한 가상주소 페이지 범위에 적용한다. backing dirty 비트를 공유하는 것만으로 다른 VA의 최초 쓰기까지 자동 포착되는 것은 아니다. [S2] VEH에서 락·할당·대기를 늘리는 변경은 기존 완료 경로와 교착하지 않는지도 확인해야 한다. [S3]

S1의 “보호되지 않은 페이지를 모두 volatile로 처리”는 **scan 대상에서 빠뜨리지 않는 정책**일 수는 있어도, 최초 쓰기 전 값과 모든 CPU 쓰기 이력을 복원하는 해법은 아니다.

## 6. volatile의 3/8 정책은 성능 휴리스틱으로 한정

보호가 꺼져 있으면 snapshot의 값 비교만으로 “8 에폭 동안 CPU store가 없었다”는 사실을 알 수 없다.

따라서 복귀 조건은 다음처럼 정의해야 한다.

> 8 에폭 동안 비교에서 값 변화가 관측되지 않으면 재보호한다.

같은 값 재쓰기·A→B→A는 관측되지 않을 수 있다. 이 조건은 재보호 시점을 정하는 휴리스틱이며 CPU 쓰기 부재나 병합 안전성의 증거가 아니다.

추가 조건은 다음과 같다.

- 내부 GPU 병합이나 prepare만 발생한 페이지를 CPU hot page로 세지 않는다.
- volatile 진입 시 기존 에폭의 미업로드 변경을 보존한다.
- 복귀 시 보호와 에폭 전환 사이의 쓰기가 어느 세대에 속하는지 정한다.
- volatile 페이지는 fault 기반 dirty 목록과 별개로 매 동기화 후보에 포함한다.
- `dm_guest_write_prepare`의 보호 전환이 생략돼도 함수 호출·dirty·snapshot bookkeeping까지 모두 사라진다고 단정하지 않는다.

정확성 규칙이 마련되기 전에는 GPU도 쓰는 페이지에 volatile을 일반 적용하지 않는 편이 변경 범위가 작다. 이는 메모리 절약 정책이 아니라 부분 갱신 보존 조건이다.

## 7. P0-5: R9에는 제출 사이의 의존성도 있어야 한다

§2.3은 제출 내부의 upload·소비자·readback·host 순서를 유지한다고 적는다. 직렬화를 제거하면 **N과 N+1 사이에서 같은 D 범위를 사용하는 순서**도 명시해야 한다.

| 앞선 작업 | 뒤의 작업 | 보장 |
|---|---|---|
| N의 GPU 읽기 | N+1 upload 쓰기 | 읽기가 끝나기 전 덮어쓰지 않음: WAR |
| N의 GPU 쓰기 | N+1 upload 쓰기 | 겹치는 쓰기의 순서 보존: WAW |
| **N readback의 D 읽기** | **N+1 upload의 D 쓰기** | **R[N]에 N+1 값이 섞이지 않음: WAR** |
| N+1 upload 쓰기 | N+1 소비자 접근 | 필요한 실행 순서와 가시성 |
| readback의 staging 쓰기 | CPU 읽기 | 완료 대기와 필요한 host 가시성 |

Vulkan의 submission order 자체는 실행·메모리 의존성을 만들지 않는다. 같은 큐에서는 범위와 stage/access가 올바른 barrier로 처리할 수 있으며, 이를 위해 항상 CPU가 `g_done`을 기다려야 하는 것은 아니다. 여러 큐가 개입하면 해당 semaphore·ownership 계약이 필요하다. [S4]

따라서 `mtl_wait(dependency)`가 담당하던 조건을 열거하고 각각을 GPU 의존성, snapshot 수명, CPU 상태 동기화로 대체해야 한다. wait 호출을 삭제하는 것만으로 전환이 끝나지 않는다.

### slice의 재사용 조건

| 대상 | 재사용·해제 가능한 시점 |
|---|---|
| upload staging | 해당 payload를 읽는 GPU copy 완료 뒤 |
| readback staging | GPU copy 완료와 CPU invalidate·비교·병합 완료 뒤 |
| 에폭 snapshot | 모든 patch 계산·병합·복구 참조가 끝난 뒤 |
| CPU dirty 상태 | 그 세대의 반영이 확정되고 이후 쓰기가 보존됐을 때 |

GPU 완료와 CPU 병합 완료는 다른 시점이다. 단순히 “그 제출이 완료되면 slice 재사용”이라고 적으면 readback을 completion 스레드가 읽는 동안 다음 GPU copy가 덮어쓸 수 있다. [S5]

GPU copy가 host에서 읽을 staging을 썼다면, 완료 대기와 필요한 invalidate 등 가시성 처리를 끝낸 뒤 읽는다. [S7]

`g_done`은 병합 뒤 release 공개, 대기자는 acquire 또는 동등한 동기화로 관측하는 기존 계약을 유지한다. 단, 병합 결과가 틀리면 올바른 공개 순서만으로 정답이 되지는 않는다.

### “남는 대기는 링이 찼을 때뿐”의 수정

일반 제출에서 전역 앞 제출 대기를 없애는 것과 모든 대기를 없애는 것은 다르다.

- 게임이 요구하는 SyncWait/QueueFinish와 CPU 결과 관측.
- CPU 캡처·페이지 커밋·alias 보호 전환의 동기화.
- readback의 CPU 병합이 끝날 때까지의 수명 관리.
- 실패 복구를 위한 성공 제출 drain.
- GPU에서 처리하는 동일 범위의 의존성.

링을 크게 잡는 것은 공간 재사용 대기를 줄인다. 위 정확성 조건의 대체물이 아니다.

## 8. P0-6: 부분 제출 실패는 상태를 먼저 분류해야 한다

S4의 “1단계처럼 전체 재동기화”만으로는 직렬화가 없는 실행의 복구가 정의되지 않는다.

### 실패 유형

| 유형 | 처리 기준 |
|---|---|
| GPU 제출 전에 준비·기록 실패 | 실행되지 않은 patch·CPU dirty를 보존 |
| 한 번의 vkQueueSubmit2가 OOM으로 실패 | 그 호출의 리소스·동기화 상태 불변이라는 명세 보장에 맞춰 처리 |
| 여러 submit 호출 중 앞 호출만 성공 | 성공한 GPU 작업과 실패한 미제출 작업을 별도로 추적 |
| DEVICE_LOST | 정상 완료·drain·재업로드가 가능하다고 가정하지 않음 |

위 OOM 보장은 한 호출에 대한 것이다. 여러 호스트 제출 호출을 하나의 트랜잭션으로 만들어 주지는 않는다. [S6]

### 필요한 복구 순서

1. 새로운 제출 준비·성공 상태와 실패 상태가 더 섞이지 않도록 복구 경계를 만든다.
2. 실제 성공한 submit과 그 완료 토큰을 확정한다. 제출되지 않은 timeline 값을 기다리지 않는다.
3. 성공한 작업의 GPU 접근을 끝내고 유효한 readback을 처리한다.
4. 성공한 GPU 쓰기는 있지만 readback 제출이 실패했다면, 정상 장치에서 **복구용 snapshot/download**가 필요한지도 처리한다.
5. 실패한 제출이 소비한 것으로 처리했던 CPU dirty·patch를 보존하고, 이후 CPU 쓰기도 놓치지 않는다.
6. G가 보존해야 할 GPU 결과와 CPU 변경을 포함한 상태가 된 뒤 새 기준을 설정한다.
7. 필요한 재업로드를 수행하고 성공한 상태만 공개한다.

옛 G를 곧바로 전체 업로드하면, 이미 성공한 다른 제출의 GPU 결과를 지울 수 있다. 현재의 잘못된 병합 규칙으로 drain만 수행한다고 해결되는 것도 아니다.

복구 중 CPU 쓰기를 통제할지, 별도 세대로 계속 기록할지도 정해야 한다. 예외 경로의 drain은 일반 제출을 다시 전역 직렬화하자는 제안이 아니다.

## 9. 4 KB 비교 최적화의 효과와 한계

64 KB 블록에서 dirty 4 KB 페이지만 비교하는 변경은 타당하다. 다만 §3의 “페이지 전체 memcmp가 없어지므로 비교량이 변경량 수준으로 줄어든다”는 결론은 틀리다.

**G와 S가 다른 바이트를 찾으려면 후보 페이지를 읽고 비교해야 한다.** 함수 이름이 memcmp가 아니어도 이 작업은 남는다.

문서의 단위를 그대로 읽으면 다음과 같다.

| 항목 | 계산·해석 |
|---|---|
| 704 MiB / 120제출 | 약 5.867 MiB, 6.152 MB/제출의 비교량 |
| 48 MB / 120제출 | 0.4 MB/제출의 업로드량 |
| 같은 64 KB 후보 블록마다 dirty 4 KB가 1개인 경우 | 단일 비교량의 이론적 최소 704/16 = 44 MiB |
| 같은 후보 블록의 16개 페이지가 모두 dirty인 경우 | 단일 비교량은 704 MiB 유지 |
| snapshot 수집·volatile 스캔·병합 | 위 단일 비교량과 별도로 집계해야 하는 비용 |

44~704 MiB는 **후보 블록 집합이 동일하고 각 후보를 한 번 비교한다는 가정의 범위**다. 실제 2단계 총 비용 예측이 아니다. 원문의 48 MB는 업로드량이며, 바이트별 실제 변경량으로 확인된 수치도 아니다.

권장 문구:

> dirty 4 KB 페이지만 비교하여 64 KB 블록의 불필요한 비교를 줄인다. 감소량은 dirty 페이지 분포에 달려 있다. snapshot 수집량, 비교량, 업로드량을 분리해 측정한다.

바이트 단위 patch를 여러 작은 GPU copy region으로 만들 때는 **region 수와 명령 기록 비용**도 집계한다. 변경 구간 사이의 미변경 구간을 임의로 합쳐 전송하면, 명시된 복사 범위의 데이터가 함께 전달되어 그 구간의 GPU 최신값을 덮을 수 있다. 복사 범위 확대는 최신 데이터 보존 조건이 있을 때만 허용한다. [S8]

## 10. 실측 해석

### HWAoI

문서의 GPU 시간 9.9 ms와 10.1 ms는 측정된 GPU 구간이 비슷하다는 근거다. 제출 완료 대기, CPU 비교, 보호 처리 경로를 우선 최적화할 근거도 충분하다.

다만 “비용은 전부 CPU에서 나온다”는 표현은 다음처럼 한정한다.

> 보고된 GPU 실행 시간은 비슷하고, CPU 측에서 측정한 제출 완료 대기·동기화·보호 처리 시간이 증가했다.

8.4~10.3 ms의 완료 대기는 CPU 계산량이 아니라 경과 시간이다. GPU 측정에 upload/readback이 포함되는지, submit+present와 세부 구간이 중첩되는지 확인해야 한다. 서로 다른 구간의 중앙값이나 범위를 단순 합산하지 않는다.

22~24 fps와 frame p50 36.2 ms는 평균 프레임률과 중앙 프레임 시간의 차이로 공존할 수 있으므로 그 자체를 산술 오류로 판단하지 않는다.

### Bayonetta 3

첨부의 copy GPU 7.4~9.0 ms, import GPU 26.6~32.2 ms는 **해당 실행에서 device-local 사본 정책이 GPU 성능 개선에 기여했다는 보고 근거**다. 이 검수에서 실행 로그를 재측정한 결과는 아니다.

깊이 패스의 “인접 패스로 넘어간 시간 포함” 표기는 단일 패스 인과 분석의 범위를 제한한다. 패스 합계와 전체 프레임도 함께 평가해야 한다.

A안을 되돌릴 이유를 제시한 검수가 아니다. 이번 문제는 **A의 비동기 캐시 일관성 규칙**이다.

## 11. 권장 진행 순서

### 11.1 먼저 독립 적용할 변경

기존 1단계의 기준본·순서 보장을 유지한 채, 64 KB 후보 비교를 4 KB dirty 페이지 비교로 바꾼다.

이렇게 하면 epoch 병합 재설계와 섞이지 않은 비교량·CPU 시간 개선을 측정할 수 있다. 기존 구현이 실제로 제공하는 정확성 범위는 별도로 유지·확인한다.

### 11.2 volatile은 정확성 조건과 분리해 도입

- 보호 전환과 prepare의 불필요한 작업을 줄인다.
- 단일 불변 캡처와 이후 쓰기 보존 규칙을 먼저 정한다.
- 내부 GPU 병합을 CPU hot-page 집계에 섞지 않는다.
- GPU도 쓰는 페이지는 동일한 volatile 규칙이 안전하다는 근거를 먼저 확보한다.

3/8 임계치 변경과 병합 알고리즘 변경을 한 수정으로 묶지 않는다.

### 11.3 직렬화 제거는 새 상태 전이를 검증한 뒤 진행

다음 계약을 문서화한다.

1. CPU write와 내부 GPU commit의 출처 구분.
2. 제출별 불변 CPU patch와 upload 성공 상태.
3. R[N] 병합 시 보존해야 할 이후 CPU 변경.
4. 이전 GPU 병합에 대한 열린 비교 기준의 보정.
5. S[N] 부재·alias·부분 제출 실패 처리.
6. 제출 간 GPU 의존성과 staging/snapshot 수명.

§2·§3 반례를 통과한 뒤 앞 제출 `g_done` 대기를 제거한다. 새로운 알고리즘을 증명하지 않은 상태에서 shadow와 wait를 동시에 삭제하는 순서는 피한다.

**앞 제출 대기 제거는 필요할 수 있지만, 기준 데이터의 역할까지 없애야 하는 것은 아니다.** CPU patch와 GPU 확정 상태를 분리해 유지하는 구조가 검토 대상이다. 구체적인 데이터 구조나 완전한 병합 알고리즘은 현재 첨부만으로 확정하지 않는다.

기존 12개 테스트의 입력·기대값이 없으므로 “교차 쓰기 2~3개 추가”만으로 커버리지가 충분하다고 판단할 수 없다.

| ID | 사례 | 합격 조건 |
|---|---|---|
| T1 | §2: CPU는 y, GPU는 x만 쓰고 N의 병합이 늦음 | N+1 완료 후 G=(2,2) |

| T11 | upload만 성공하거나 GPU 실행 후 readback 제출 실패 | 성공 GPU 결과·미제출 CPU patch 모두 보존 |
| T12 | 실패 복구 중 추가 CPU 쓰기 | 재동기화가 새 쓰기를 지우거나 없는 토큰을 기다리지 않음 |

이는 새 성능 벤치가 아니라 캐시의 상태 전이를 검증하는 합성 정확성 사례다. 취소한 동일 주소 픽셀 벤치나 DK 실행을 요구하지 않는다.

기존 12개 테스트는 모두 재실행한다. import에서도 남는다는 counter 1건은 기대 결과와 기존 결함을 별도로 표시한다. **기존 결함과 같은 결과라는 사실만으로 해당 기능의 정확성이 증명된 것은 아니며, copy에 새로 생긴 회귀와 구분해야 한다.**

### 같은 게임 실행에서 필요한 계측

- 전역 앞 제출 대기와 기타 대기 시간을 분리.
- dirty 4 KB 페이지 수, snapshot 생성·복사·비교 bytes 및 CPU ms.
- GPU 내부 병합 bytes와 게스트 CPU patch bytes를 분리.
- upload bytes뿐 아니라 copy region 수·명령 기록 시간.
- GPU upload·draw/dispatch·readback 시간의 측정 범위.
- GPU 완료부터 CPU 병합·g_done 공개까지의 지연.
- 실제 page protection 전환 수, prepare 호출 수, fault/s와 처리 시간.
- 프레임 p50/p95, GPU 전체 시간, 게임 결과 정확성.

60 fps는 목표다. 4 KB 비교나 volatile 임계치만으로 달성되는 사전 보장값은 아니다.

## 14. 반영용 결론

> 2단계의 목표는 유지하되, G와 첫 쓰기 snapshot의 차이를 CPU 변경으로 간주하는 현재 규칙은 사용하지 않는다. 이전 GPU 커밋이 열린 에폭의 기준에 반영되지 않아 새 GPU 결과가 유실되거나 오래된 값이 다시 업로드되는 반례가 확인됐다. CPU patch와 GPU 커밋의 출처·버전을 분리하고, 불변 업로드 payload, 열린 기준의 정합성, 제출 간 GPU 의존성, readback CPU 병합까지의 수명을 명시한다. 4 KB dirty 비교는 기존 정확성 경로에서 먼저 독립 적용하며, 직렬화 제거는 해당 상태 전이 검증 뒤 진행한다.

## 부록 A. 실행한 모델의 규칙과 결과

모델은 설계 §2.1·§2.2의 식을 아래처럼 적용했다. 실제 게임 코드의 구현을 옮긴 것이 아니다.

~~~python
def merge_doc(base, guest, readback):
    return [
        r if r != b and g == b else g
        for b, g, r in zip(base, guest, readback)
    ]

def diff_doc(base, guest):
    return {
        i: g
        for i, (b, g) in enumerate(zip(base, guest))
        if g != b
    }

def upload(device, patch):
    out = list(device)
    for i, value in patch.items():
        out[i] = value
    return out
~~~

### 문서 판정식의 직접 반례

~~~python
S_N = [0, 0]
R_N = [1, 0]

# 다음 GPU 제출의 결과와 다음 CPU 쓰기 직전 snapshot
D = [2, 1]
R_N1 = [2, 1]
S_N1 = [0, 1]
G = [0, 2]

# N 병합은 CPU y=2를 보존하며 GPU x=1을 반영한다.
G = merge_doc(S_N, G, R_N)
assert G == [1, 2]

# 분기 A: N+1 병합은 잘못된 x=1을 유지한다.
assert merge_doc(S_N1, G, R_N1) == [1, 2]
# 기대값은 [2, 2].

# 분기 B: N+2 업로드는 이미 최신인 D.x=2를 1로 되돌린다.
patch = diff_doc(S_N1, G)
assert patch == {0: 1, 1: 2}
assert upload(D, patch) == [1, 2]
# 기대값은 [2, 2].
~~~

### 캡처 계약이 차단해야 하는 조건부 반례

~~~python
G = [1]
upload_payload = list(G)
G[0] = 2                   # upload 캡처 뒤 CPU 쓰기
next_baseline = list(G)     # 다른 시점의 G로 기준을 설정

D = list(upload_payload)
assert D == [1]
assert diff_doc(next_baseline, G) == {}
# GPU에 2를 보내지 않았지만 다음 비교에서 누락된다.
~~~

실행 결과:

| 사례 | 모델 결과 | 올바른 결과 | 구분 |
|---|---|---|---|
| 이전 GPU 병합을 CPU 쓰기로 오인 | G=(1,2) | G=(2,2) | 문서 판정식의 직접 반례 확인 |
| 이전 GPU 값을 다음 업로드에 포함 | D=(1,2) | D=(2,2) | 문서 판정식의 직접 반례 확인 |
| 서로 다른 캡처를 upload와 기준에 사용 | D=1, G=2, 다음 patch 없음 | 2의 반영 또는 dirty 보존 | 캡처 계약에서 배제해야 할 순서 확인 |

세 사례를 Python으로 실행하여 표의 결과와 불일치를 확인했다. 추가 GPU 벤치나 프로젝트 테스트를 실행한 것으로 해석하면 안 된다.
