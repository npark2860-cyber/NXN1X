# GPU 메모리 캐시 2단계 설계: 직렬화 제거, 4 KB dirty 비교, volatile 페이지

작성일은 2026-11-20입니다. **설계안이며, 아스트라 검수와 NPARK 승인 전에는 구현하지 않습니다.**

## 0. 왜 하나: 1단계 copy 모드 실측 (HWAoI, 평소 테스트 지점, 16:01 실행)

| ② 사본 동기화 | 프레임당 5.8~6.8 ms (제출당 약 6 MB 비교, 120제출에 704 MiB 비교 / 48 MB 업로드) | 없음 |

GPU 시간은 그대로입니다. 비용은 전부 CPU에서 나오고, 원인은 1단계의 정확성 우선 단순화 세 가지입니다.
1. ① 직렬화: 사본 기준본(shadow)이 "제출 시작 때의 사본 내용"이 되도록, 각 동기화가 앞 제출의 완료와 병합을 기다립니다.
2. ② 64 KB 블록 단위 동기화: dirty 페이지가 하나라도 있는 64 KB 블록 전체를 비교합니다.
3. ③ 매 동기화마다 재보호: 매 프레임 쓰이는 페이지가 계속 보호되어, 쓸 때마다 예외가 납니다.

## 1. 핵심 아이디어: 기준본을 "제출 시작 때 사본"에서 "에폭별 첫 쓰기 스냅숏"으로

1단계에서 shadow가 맡던 역할은 두 가지입니다.
- (a) 업로드할 CPU 변경분을 찾는 비교 기준
- (b) 병합 때 "GPU가 바꾼 바이트"와 "CPU가 바꾼 바이트"를 가르는 기준

둘 다 "사본의 그 시점 내용"이어야 해서 직렬화가 필요했습니다.

2단계에서는 **동기화 에폭**(epoch, 제출마다 1씩 증가)을 둡니다. 기준은 **각 에폭에서 그 페이지의 첫 CPU 쓰기 직전 내용**(스냅숏)입니다.
- 스냅숏 수집: 동기화 때 dirty 페이지를 다시 보호합니다(지금과 같음). 이후 그 페이지의 첫 쓰기 예외에서 쓰기 직전 내용을 `S[e](P)`로 보관합니다. 기존 `snap_hook`을 확장합니다.
  - 메모리는 제약이 없으므로(NPARK 15:02) 해시 슬롯 충돌로 버리지 않습니다.
  - 페이지와 에폭마다 하나씩 두고, 그 에폭의 병합이 끝나면 해제합니다.
- 핵심 성질: **그 에폭에 CPU가 바꾼 바이트는 `G ≠ S[e]`로 바이트 단위로 정확히 구분됩니다.**
  - GPU가 쓴 바이트는 병합 전까지 게스트에 반영되지 않습니다. 그래서 `G == S[e]`인 바이트는 CPU가 바꾸지 않은 것입니다.

## 2. 직렬화 제거 (①)

### 2.1 업로드 (제출 N의 동기화, 앞 제출을 기다리지 않음)
- 대상: 직전 에폭 이후 CPU가 쓴 페이지(nvn_dirty 세대)
- 페이지마다:
  - 스냅숏이 있으면 `G ≠ S[e](P)`인 바이트 구간만 올립니다.
  - 스냅숏 없이 dirty이면(첫 동기화 등) 페이지 전체를 올립니다.
- 올릴 바이트는 **제출별 staging slice**(host-visible, 그 제출이 완료되면 재사용)에 복사합니다. 그다음 staging → device-local GPU 복사를 업로드 명령 버퍼에 기록합니다.
  - shadow를 원본으로 쓰지 않으므로, 앞 제출의 업로드 복사가 아직 안 돌았어도 덮일 일이 없습니다.
- 바뀐 바이트만 올리므로, 앞 제출(진행 중)이 GPU로 쓴 바이트는 사본에 그대로 남습니다.
  - 같은 바이트를 둘 다 바꿨다면 CPU 값이 이깁니다. 큐 순서상 업로드가 나중이고, 병합 규칙(2.2)과 같은 결론입니다.
- 이후 그 페이지는 다시 보호하고 에폭을 올립니다.

### 2.2 되돌림 (제출 N 완료 시, 완료 스레드는 제출 순서대로)
- readback 범위(1단계와 같음: 쓰기 목록, 크기 미상이면 청크 전체)마다 R = 사본의 제출 끝 내용입니다.
- 페이지별 판정:
  - 에폭 N 이후 CPU가 쓰지 않은 페이지: 게스트가 곧 "N이 쓰기 전의 사본 내용"입니다(앞 병합은 순서대로 끝났고, N의 업로드는 이 페이지에 없음). 그래서 `R ≠ G`인 바이트를 R로 씁니다.
  - 에폭 N 이후 CPU가 쓴 페이지: 기준 `B = S[N](P)`입니다. `R ≠ B`이고 `G == B`인 바이트만 R로 씁니다. `G ≠ B`이면 CPU 값을 둡니다.
  - 에폭 N+1 이후 쓰기(이미 다음 제출 동기화가 지나간 경우): `S[N+1](P)`가 있으면 그 페이지는 N+1 에폭에서도 CPU가 썼다는 뜻입니다. 같은 규칙에 기준만 `S[N]`을 씁니다. CPU 바이트(`G ≠ S[N]`)는 보존됩니다.
- 쓴 바이트는 `dm_guest_write_prepare` 뒤에 씁니다. 그러면 페이지가 dirty로 기록되어 다음 동기화가 그 바이트를 비교합니다. 이미 사본과 같은 값이라 실제 업로드는 없습니다.
- shadow 버퍼(1단계)는 없앱니다. readback slice는 제출별입니다.

### 2.3 검수 R9 순서 유지
업로드 staging의 host write → transfer read → 소비자, 마지막 쓰기 → readback transfer → host read, timeline 완료 → 병합 → `g_done`. 1단계 순서를 그대로 지킵니다. 바뀌는 것은 "다음 제출의 CPU 동기화가 앞 제출의 `g_done`을 기다리지 않는다"는 점 하나입니다.

### 2.4 남는 대기
- staging과 readback slice 링이 꽉 차면 그 제출의 완료를 기다립니다. 메모리 제약이 없으니 링을 크게 잡습니다.
- 게임의 펜스 대기(`nvnSyncWait`/`nvnQueueFinish`)는 지금처럼 병합 후 `g_done`을 기다립니다.

## 3. 4 KB dirty 비교 (②)
- `pool_sync_one`의 64 KB 블록(`BLK`)을 4 KB 페이지로 바꾸고, nvn_dirty가 dirty라고 한 페이지만 처리합니다.
- 2.1의 스냅숏 비교로 바뀐 바이트만 찾으므로, 1단계의 `pool_sync_copy` 페이지 전체 memcmp도 없어집니다.
- 예상: HWAoI 120제출 704 MiB 비교 중 실제 변경은 48 MB입니다. 비교량이 변경량 수준으로 줄어듭니다.

## 4. volatile 페이지 (③)
- 3번 연속 에폭에서 CPU가 쓴 페이지는 volatile로 바꿉니다(vbvol의 `VBM_VOL_HITS = 3`). 보호를 풀어 쓰기 예외가 나지 않게 합니다.
- volatile 페이지는 **매 동기화마다 기준 스냅숏을 직접 찍습니다**(예외 대신 동기화 시점에 `S[e](P) = G`).
  - 업로드는 "직전 에폭 스냅숏 대비 바뀐 바이트"만 올립니다.
  - 병합 규칙은 2.2와 같습니다.
  - 비용은 volatile 페이지 수 × 4 KB 복사·비교/제출입니다. vbvol 실측은 0.4 MB였습니다.
- 8 에폭 연속 쓰이지 않으면 다시 보호합니다(복귀).
- 호스트 사전 해제 8만 건/s: 호스트(HLE)가 게임 메모리에 쓰기 전 `dm_guest_write_prepare`가 보호를 푸는 횟수입니다. volatile 페이지는 보호가 없어서 이 비용도 함께 사라집니다. 남은 비용은 7절 측정으로 확인합니다.

## 5. 1단계 대비 변경 요약
- 없앰: 동기화 전 `mtl_wait(dependency)`(copy 모드), shadow 버퍼, 64 KB 블록 비교
- 추가: 에폭, 페이지별 에폭 스냅숏 저장소, 제출별 staging/readback 링, volatile 상태
- 유지: device-local 사본(backing 범위 공유), 쓰기 목록·크기 미상 처리, 거부 제출 재동기화, 완료 스레드 순서, 이벤트·카운터 보호 해제(poolcopy2), tebfix2

## 6. 위험
- **S1 스냅숏 누락**: 첫 쓰기 예외를 거치지 않는 CPU 쓰기가 있으면 G ≠ S 구분이 깨집니다. 보호가 없는 페이지, 다른 VA alias로 쓰는 경우, DMA처럼 호스트가 prepare 없이 쓰는 경우입니다.
  - 대책: 보호되지 않은 페이지는 전부 volatile(동기화 시점 스냅숏)로 처리합니다. alias view는 backing 범위로 dirty를 공유해야 합니다. 이 부분은 검수가 필요합니다.
- **S2 진행 중 제출이 여러 개일 때 병합 규칙의 정확성**: 2.2 판정을 합성 테스트로 검증합니다. 같은 바이트를 CPU·GPU·다음 제출이 번갈아 쓰는 경우를 포함합니다.
- **S3 스냅숏 저장소 크기**: 진행 중 에폭 × CPU 쓰기 페이지 수만큼 커집니다. 메모리 제약은 없지만 수명 관리가 필요합니다.
- **S4 부분 제출 실패와 에폭**: 거부된 제출의 업로드가 실행되지 않으면 사본과 에폭이 어긋납니다. 1단계처럼 전체 재동기화로 처리하되, 진행 중인 다른 제출과의 순서를 다시 확인해야 합니다.

### 8.2 새 직렬화 제거 방식: GPU 측 사전·사후 readback과 "G의 거울"인 shadow

1·2절의 첫 쓰기 스냅숏 방식을 버립니다. 판정 근거를 **CPU가 추측하는 기준본에서 GPU가 실제로 본 값으로** 옮깁니다.

1. **shadow의 의미 재정의.** shadow는 "마지막 캡처 이후 CPU 변경을 뺀 게스트 값"입니다.
   - 캡처 때: dirty 페이지에서 `G ≠ shadow`인 바이트를 CPU patch로 만들고 shadow를 그 값으로 바꿉니다. 캡처 C[N] 하나를 payload와 새 기준에 같이 씁니다(P0-4).
   - 병합 때: G와 shadow를 **같은 값으로 함께** 갱신합니다.
   - 그래서 `G ≠ shadow`는 항상 아직 캡처하지 않은 CPU 쓰기만 뜻합니다. 이전 GPU 병합이 CPU 변경으로 보이는 일이 없습니다(P0-2).
   - 캡처(replay 스레드, 풀 쓰기 잠금)와 병합(완료 스레드, 풀 잠금)은 1단계처럼 서로 배타적으로 실행됩니다.
2. **업로드.** patch를 제출별 staging에 불변으로 담고, staging → 사본 GPU 복사를 업로드 명령 버퍼에 기록합니다. 업로드 명령 버퍼 첫 barrier(ALL_COMMANDS MEMORY_READ|WRITE → TRANSFER)의 첫 범위에는 앞 제출들의 명령이 포함됩니다. 그래서 N의 readback 읽기, N의 GPU 쓰기와 N+1 업로드 쓰기 사이의 WAR/WAW가 지켜집니다(P0-5).
3. **사전·사후 readback.** 쓰기 범위마다 그 범위를 처음 쓰는 part의 업로드 명령 버퍼 끝에 `사본 → pre[N]` 복사를 넣습니다. 그 part의 업로드 뒤, GPU 쓰기 전에 실행됩니다. 제출 끝에는 `사본 → post[N]` 복사를 넣습니다.
   - part를 일찍 보낼 때(`vk_cmd_split`)는 그때까지 알려진 쓰기 범위의 pre를 그 part의 업로드 명령 버퍼에 넣습니다.
   - 크기 미상이나 raw 쓰기는 1단계처럼 청크 전체를 대상으로 합니다.
   - **GPU가 N에서 바꾼 바이트는 `post ≠ pre`로 정확히 알 수 있습니다.** CPU 쪽 기준본이 필요 없습니다.
4. **병합(완료 스레드, 제출 순서).** `post[N] ≠ pre[N]`인 바이트마다 처리합니다.
   - `G == pre`이면 G와 shadow에 post를 씁니다.
   - `G ≠ pre`이면 N의 캡처 뒤에 CPU가 그 바이트를 썼다는 뜻입니다. 앞 제출의 병합은 순서대로 이미 끝났기 때문입니다. CPU가 나중이므로 G를 두고 shadow만 post로 바꿉니다. 사본은 다음 캡처 때 CPU 값으로 다시 맞춰집니다.
   - (x,y) 반례 검산: N 병합에서 x는 pre 0, post 1, G 0이므로 1을 씁니다. N+1 병합에서 x는 pre 1, post 2, G 1이므로 2를 씁니다. 결과는 G=(2,8)입니다. N+2 업로드는 G(1,8)과 shadow(1,7)을 비교해서 y만 올리고 x는 그대로 둡니다.
   - pre, post, 쓰기 범위, backing 세대, 접수된 part는 **그 제출이 소유**합니다. 풀의 `rb_sub` 같은 공유 상태는 쓰지 않습니다.
   - slice는 그 제출의 병합이 끝난 뒤 반환합니다(P0-5 수명).
5. **부분 실패(P0-6).**
   - 앞 part만 접수됐다면: 접수된 part들의 쓰기 범위에 대해 별도 복구 제출(post 복사)을 보냅니다. 그것만 기다리고 병합합니다.
   - 거절된 part의 업로드 patch: 캡처 때 덮어쓴 shadow 바이트를 원래 값으로 되돌립니다. 그러면 그 CPU 변경이 다음 캡처에서 다시 잡힙니다.
   - 접수 여부를 확정할 수 없는 장치 오류(DEVICE_LOST)는 정상 복구로 처리하지 않습니다.
6. **남는 대기.** 게임의 SyncWait/QueueFinish, 링 포화, 그리고 다음 제출이 CPU에서 해석해야 하는 앞 제출 결과가 있습니다. 후자는 그 범위의 병합을 기다립니다. `pool_sync_one`의 할당별 `wait_fence(use)`도 이 기준으로 다시 정리합니다.

### 8.3 구현 순서 (단계마다 따로 측정·검수)

1. **CPU 쓰기 누락 수정 + 4 KB 선별.** 대기와 shadow는 그대로 둡니다.
   - `ObserveGuestWrite` 경로(`Memory::Write*`, 성공한 `WriteExclusive*`)가 dirty를 기록하게 합니다.
   - 64 KB 후보 선별을 4 KB로 바꿉니다.
   - 측정: 탐색 횟수, 검사한 페이지, 읽은 바이트, 업로드 바이트, 복사 명령 수, CPU ms
2. **CPU 전용 페이지 volatile.** GPU 쓰기 목록에 한 번도 나온 적 없는 페이지에만 적용합니다. 캡처 C[N] 하나를 payload와 새 기준에 같이 씁니다.
   - 진입: 3회 연속 값 변화. 복귀: 8회 값 변화 미관측. 둘 다 성능 휴리스틱입니다.
   - 내부 병합과 prepare만 있었던 페이지는 횟수에 넣지 않습니다.
3. **8.2 직렬화 제거.** 1·2를 측정한 뒤, 8.4 테스트를 먼저 작성하고 진행합니다.
